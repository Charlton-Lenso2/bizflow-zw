# BizFlow ZW — Architecture

## 1. Purpose

BizFlow ZW is a mobile-first business management application for small businesses in Zimbabwe. The initial pilot is a real wholesale business.

The architecture should support reliable financial records, secure business data, and future expansion without overengineering the capstone.

## 2. System Overview

The application is divided into:

- Frontend: React + TypeScript + Vite
- Backend: Node.js + Express + TypeScript
- Database: Supabase PostgreSQL
- Authentication: Supabase Auth
- AI provider: Gemini API
- API style: REST

The frontend communicates with the backend through documented API contracts.

The backend validates requests, enforces business rules, authorises access, and performs database operations.

## 3. Core Architectural Rules

1. Financial calculations and ledger balances are authoritative on the backend/database, not in the AI model.
2. USD and ZiG transactions remain separate. No implicit currency conversion or combined balances.
3. A sale or credit charge is recorded as an immutable business event.
4. Payments are recorded as separate events and linked to the relevant sale or credit account.
5. Partial payments must be supported.
6. Corrections and refunds must be represented through traceable adjustment records rather than silently overwriting financial history.
7. All business data access must be scoped to the authenticated user's authorised business.
8. Secrets and private API keys must never be exposed in frontend code.
9. AI responses must be grounded in authorised business data and must not invent missing records or balances.
10. AI must not create or modify financial records without an explicit user-confirmed workflow.
11. Receipts generated by this capstone must be labelled NON-FISCAL.
12. Offline synchronisation is a stretch goal and must not delay the online core workflows.

## 4. Authentication and Authorisation

Supabase Auth will manage user authentication.

The backend must verify the authenticated user's identity and business membership before allowing access to business data.

Database policies and backend checks must prevent users from accessing another business's records.

## 5. Financial Data Principles

- Store currency explicitly on every relevant financial record.
- Use appropriate fixed-precision numeric database types for monetary values.
- Avoid floating-point arithmetic for authoritative financial calculations.
- Preserve transaction history.
- Calculate outstanding balances from recorded charges, payments, and adjustments.
- Validate that payments use the same currency as the balance they settle unless a future, explicitly designed exchange workflow is introduced.

## 6. AI Assistant

The AI assistant will use backend-controlled tools to retrieve relevant business data.

The backend is responsible for:
- Authentication and authorisation
- Validating tool inputs
- Running deterministic queries and calculations
- Returning only the data the user is allowed to access
- Recording relevant audit information

The AI provider must not receive unrestricted database credentials.

If the AI service is unavailable, core business workflows must remain usable.

## 7. Deployment

The frontend and backend may be deployed separately.

Deployment providers will be selected after the application structure, environment requirements, and pilot needs are confirmed.

## 8. Out of Scope for the Capstone

- ZIMRA FDMS fiscalisation
- Guaranteed offline synchronisation
- Unvalidated enterprise resource planning features
